# Junker helmet scanner

Scanner mode applies a mild URP color adjustment through the player's camera: saturation defaults to -12, contrast to -4, and exposure to 0. Tune these in `HelmetScannerController` under **World treatment**. The volume and camera post-processing state are disabled/restored when scanning ends, so the effect has no ongoing cost outside scanner mode. The existing `ScannableObject`/`ScanHighlightTarget` registrations use soft white-gray for ordinary interest; faults, cut guides, and installation targets retain their semantic colors. Tune those colors in `DefaultScannerVisuals` or another `ScanVisualProfile`.

The scanner uses the existing tracked headset/controllers and their `AnimateControllerHand.triggerValue` actions. Raise either hand beside either temple, press the trigger, then lower the hand. A new press is required to toggle again. Holding the trigger while entering a zone does not toggle. The rig's existing Input Action Manager owns action enable/disable; the scanner never disables shared actions.

`HelmetScannerController` exposes hand permissions, two head-local offsets and radius, an optional head-attached collider (replaces the radius zones), trigger thresholds, cooldown, view sphere radius, range, update interval, scannable/obstruction masks and a player hierarchy to ignore. Defaults: 13 cm activation radius, 450 ms debounce, 8 m range, 12 cm view sphere, 10 Hz queries. The optional collider must be a trigger if it should not physically block hands.

## Existing project integration

Use **Tools > Junker > Scanner > Configure existing hoverbike POC**. Setup modifies the existing `Assets/MyAssets/prefabs/ground vehichles/Junk Hover Bike.prefab` and wires the existing `VRBodyController` in `Assets/Scenes/JunkerBody.unity`. It does not recreate the vehicle or change flight/drive controls. Setup preserves subsequent scanner tuning when rerun. An already-dirty open scene is left unsaved so the tool does not save unrelated user edits.

The vehicle displays GRASSHOPPER HOVERBIKE, with Power System, Lift Engine and Cooling operational. Thrust Controller references a `ComponentSlot` containing a zero-condition TCU-04, giving Fault. Emptying that slot gives Missing. `HoverBikeController.requiredDriveSlots` now includes that slot: a missing or below-threshold TCU blocks drive, hover lift, boost and engine audio. Inserting a healthy one restores them.

`Scanner POC - Right Service Bay` is the right-side service bay. Loosen every screw, **grip the cover and move it away**, then release it at its storage anchor. The failed TCU is immediately behind the opening and becomes grabbable only after the cover opens the compartment. Grip it to pull it out. `Assets/MyAssets/prefabs/Tools/Fresh TCU-04.prefab` is the healthy replacement, using the authored ThrustController housing from the demo scene. Release it near the open socket; its collider can enter the **Install Radius** and it snaps into the **TCU Installation Pose**. The bike's original drive switch must still be on to drive. Both failed and fresh TCUs have `VRInventoryItem`, so either can be placed in the open backpack and retrieved later. Use **Tools > Hover Bikes > Configure replaceable TCU and power gate** to reapply prefab and loaded-scene wiring.

The TCU Installation Pose is a bike-parented JunkerEquipmentSlot accepting item ID TCU-04. Its Starting Item is the authored broken TCU. Both TCUs are JunkerEquipmentItems and backpack items. Equipment mounting owns their pose, using the same mechanism as body tool slots; SalvageComponent does not move mounted TCUs. The bike checks the equipment slot occupant and its condition for drive power. Installed module physics remains outside the bike hierarchy while the slot stays parented to the bike. Their physical colliders ignore the bike hull and the detached service cover, while XR hand overlap remains available once the cover is removed. Leave `SalvageComponent` enabled during normal play; it manages the grab gate and the occupied socket.

The reusable `Assets/MyAssets/prefabs/Player/JunkerWeapon.prefab` now also contains the complete scanner and HUD, so newly placed character instances need no scene-only scanner setup. Reusable screw-fastened covers with storage and snap-back are documented in [RepairPanels.md](../JunkerEquipment/RepairPanels.md).

In Play mode, use the `ServiceCompartment` component's **Open compartment (scanner hook)** context menu to expose the TCU for inspection, or assign it to a `JunkerRepairPanel`. The repair panel calls `SetOpen(true)` when its cover is grabbed and `SetOpen(false)` when the cover snaps closed. Loosening screws alone does not open scanner access.

The HUD is a compact head-relative TextMeshPro object, wired through `ScannerPresenter`. It shows a small online indicator when no target is selected and concise information on focus. Optional on/off audio clips and source are unassigned. Adjust font size, position and dimensions on a headset as needed.

## Authoring

* **Any object:** add a collider and `ScannableObject`, fill the optional name/category/status/description/hint, and ensure its layer is included in the scanner mask. Trigger colliders are supported. A collider resolves the nearest ancestor `ScannableObject`; put child components on their own collider objects for finer focus. Priority is a small bounded preference, not a substitute for sensible collider geometry. Inactive components and closed-compartment contents cannot be selected.
* **Visuals:** add `ScanHighlightTarget`, explicitly assign only the intended renderers, and assign it to the scannable's highlights. One highlight target should own each renderer. Set the semantic category on the scannable. `DefaultScannerVisuals.asset` centralizes colors; subclasses can replace the highlight backend. The current backend tints material property blocks, preserving material identity and restoring the original per-material blocks. Do not have another system write the same renderer property blocks during a highlight; compose those effects in a shared backend if needed. URP Lit base colors are supported; custom shaders can supply a backend.
* **Machine diagnosis:** add `DiagnosticSystem` and include it in the scannable's ordered `providers`. Author module names, static status or a real slot, severity/message, physical location and highlight reference. Fault entries make the overall status Fault. On focus, their highlight targets get the Fault semantic. Multiple modules can share a location. Messages and locations remain available to replacement presenters.
* **Salvage:** add `SalvageComponent` and include it in `providers`. Set ID/type, display name, condition 0–100, compatibility tags and removability. A loose functional part reports Salvageable; zero condition reports Fault; an installed part reports its functional condition. Use `gameplayData` for a future custom stat asset. Add a scannable/collider and use the Salvage highlight category.
* **Installed parts:** configure `ComponentSlot` with accepted component type and equipment tag (empty means unrestricted), initial occupant, installation transform, accessibility and optional compartment. `TryInstall` rejects occupied, incompatible or inaccessible slots and parts already in another slot. `TryRemove` respects accessibility/removability. Slot `Status` is live, derived from the actual occupant. `Changed` reports occupancy changes; condition changes are read on the next scan. A part with Rigidbody and XR Grab Interactable can be gripped out of an open slot and snaps in when released within **Install Radius**; its grab is disabled while the compartment is closed. Data-only parts still work. With an optional `JunkerEquipmentSlot` mount, physical mounting delegates to the equipment system.
* **Service bay:** add `ServiceCompartment` as a data provider, set its name and diagnostic references, and give the bay its own scannable/collider/highlight. Assign it as `accessCompartment` on interior scannables and as `compartment` on slots. Call `SetOpen` from your actual access interaction. The bay's scannable carries the optional hint/description.
* **Cut access:** add `CuttableAccessPoint` as a provider on a scannable. Set required action/tool text, material rating, difficulty, opened state and paths. For each path add `AuthoredCutPath` and a LineRenderer, assign child control-point transforms, optional closed loop, line material/width and visual profile. No spline package is needed. Eligible visible nearby panels reveal their guide while scanning. `path.RequestVisibility(owner, true/false)` allows a future cutter to hold visibility independently of the scanner. Each owner must release its request on disengage/disable. Call `SetOpened(true)` after future cutting; scanner ownership is released on its next update. A path follows moving control points in local coordinates.

Nearby highlighting uses visible colliders in the forward view cone. Focus uses a forgiving view spherecast with alignment, distance, bounded priority and slight focus hysteresis. Opaque colliders in the obstruction mask block inspection. Fault targets may be highlighted on the focused machine even if not directly aimed at; this is diagnostic localization. There is no through-wall rendering or post-processing. Range/frequency/visual backend/presenter can be changed independently. No global per-frame scannable search or runtime `FindObjectOfType` is used.

## Files and validation

New runtime framework files live here; editor tools live in the project's existing `Assets/Editor` folder:

* `ScanData.cs`, `ScannableObject.cs`: contracts, optional data and composed providers.
* `HelmetScannerController.cs`: gesture, state, physics selection, focus and visual ownership.
* `DiagnosticSystem.cs`, `SalvageComponent.cs`, `ComponentSlot.cs`, `ServiceCompartment.cs`: domain data and access hooks.
* `ScanVisualProfile.cs`, `ScanHighlightTarget.cs`: central styling and replaceable safe tint backend.
* `AuthoredCutPath.cs`, `CuttableAccessPoint.cs`: authored guide geometry and cutter-facing visibility API.
* `ScannerPresenter.cs`, `CompactScannerPresenter.cs`: replaceable UI contract and TMP implementation.
* `../Editor/HelmetScannerSetup.cs`: repeatable integration with existing assets.
* `../Editor/HelmetScannerValidation.cs`: isolated Unity contract and physics checks.
* `DefaultScannerVisuals.asset`, `ServiceBayPlaceholder.mat`, this README, and Unity `.meta` files.

Existing systems reused: `VRBodyController` tracking, `AnimateControllerHand` trigger actions, the existing Input Action Manager, optional `JunkerEquipmentSlot`/`JunkerEquipmentItem` physical mounting, TextMeshPro, URP materials, and the original hoverbike prefab/hull. The existing ship `SubsystemController` models combat heat/damage rather than removable equipment; it is not duplicated or changed. A future `ScanInfoProvider` can adapt it.

Run **Tools > Junker > Scanner > Validate scanner contracts**. Tests cover gesture edges/cooldown/hand permissions, slot compatibility/ownership/removal, closed bay gates, salvage data, shared highlight restoration, multi-owner cut visibility, view selection, occlusion, child focus, range, and shutdown cleanup. Tests use temporary objects and close their temporary scene. Setup writes the result to `Library/HelmetScannerWork/result.txt`.
